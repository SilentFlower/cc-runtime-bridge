# 技术设计

## 1. 两类输入与共同边界

- 在共享输入解析边界识别 `api` 与 `claude_code`，由服务端写入接入类型，不能把调用方提供的任意模式标记当成权限。分流结果和原生关联证据随 PreparedInput 一起进入私有工作进程。
- 普通 API 继续采用现有 MessageBody 支持范围和显式上下文信封，省略 tools 表示无工具；新增原生分支不自动扩大该分支的字段范围。
- 原生分支要求唯一、可解析的根 system billing、匹配固定 293 的版本及有效 metadata.user_id 结构；检查头部、billing、metadata 和显式上下文的一致性。疑似原生但证据损坏、版本不支持或冲突的输入明确拒绝，不回落到普通 API 后重新拼装。
- UA 只作为辅助证据，不用于授予凭据、执行或本地配置权限。完整原生正文及扩展数据只传向固定上游 Messages 路径；不能用于指定二进制、代理、工作目录、账号或发送目标。
- 原生正文类型保留上游 JSON 扩展，而本机控制字段继续由既有配置合同独占；为禁止的控制字段建立明确定义与反例，拒绝优先于静默删除。

## 2. 原生业务正文保留及身份归属

| 内容 | 行为 |
| --- | --- |
| system 的业务段、顺序和缓存标记 | 保留，不再调用 VA/Kz 的输出替换这些段落 |
| messages 及 thinking/tool_use/tool_result 等块 | 保留原 JSON 语义、顺序、签名和缓存位置，不加 CLI 提醒 |
| tools、tool_choice、output_config、thinking 和显式采样参数 | 保留声明和省略状态，不自动补工具、strict 或默认值 |
| thread、diagnostics、fallbacks、safeguards 及合法扩展 JSON | 原生分支保留，不解释为本机执行指令或配置 |
| metadata.user_id 中 device_id、account_uuid | 使用当前专用账号运行时生成的身份来源，不能沿用调用方账号凭据或设备归属 |
| metadata.user_id 中 session_id | 使用原生证据解析且冲突校验后的会话；其他 metadata 数据按明确合同保留，不批量清空 |
| billing 版本、会话后缀、prompt/轮次及父子信息 | 核对固定版本并保留可证明的入站值，冲突时拒绝，不用新的占位消息重算原生业务后缀 |
| billing 的最终 CCH | 发送前使用原生占位表示，由实际原生传输生成最终值；独立复算只用于验证 |
| Authorization、传输/运行时头 | 当前专用账号及 SDK 提供；Host、长度等按实际发送重建 |
| 端到端扩展、分类、父子及协议条件头 | 在既有头部策略上保留并与已解析上下文校验；未知条件不能静默删除 |

保真是 JSON 语义及字段/块顺序、缓存位置的合同；必要的身份改写和 JSON 编码会改变完整正文哈希。原始 HTTP 入站字节、改写后中间值、最终接收字节分别记录，不能混称。

## 3. 复用已验证的原生发送边界

- 普通 API 路径继续通过真实 CLI 构造流程生成请求，修复错误传播和有效工具历史的挂起，不换成录制模板。
- 原生路径复用当前工作进程、每轮独立原生根，以及同一 SDK 的构造/传输上下文。在唯一 fetchOverride 边界使用经过保真核验及必要身份改写的原生正文，而非让 OM 重新解释完整入站历史、重组提示词。
- 获取 SDK 发送上下文所需的本地构造只为账号/传输服务；其默认正文不得混入原生请求、不得产生第二次业务请求或独立业务日志，也不创建第二个客户端。
- 对原生替换后的正文做逐字段核对，再调用唯一 Ree。该调用仍受单次发送守卫保护，SDK 永远不能消费上游 Response；桥接保持原始逻辑响应所有权。
- 实施第一步先以原版固定源进行小规模原生发送证明，确认同一上下文下保留业务段、正确归因及原生最终 CCH 均成立，再扩展实现与精简构建。若当前接口不能满足合同，停在技术证据并同步设计，不以 JS 补签、第二个 SDK 或复制模板代替。

## 4. 校验、错误和生命周期

- 入口验证 JSON 形状、工具声明与选择、上下文冲突、原生版本和私有控制字段；模型与 thinking 兼容表仅来自固定 293 的实际定义和原版离线验证，不照抄 vm2api 303 的常量。
- 固定版本不支持的工具组合返回有具体原因的 4xx。构造器抛错、返回失败事件或在发送前结束时，均须让 responseReady/作业得到确定失败，不忽略错误后等待整体预算。
- 两个有效历史超时场景须定位到实际阶段及根因，再修复。新的异步失败路径必须收口原生任务、释放 Response 和取消订阅；终态与 idle、异常退役、下一作业独立重建合同不变。
- 不重试模型、不执行本地工具、不触发代理循环或自动压缩。显式 compaction 及辅助请求按真实类别处理。

## 5. 日志及页面

- 五段采集与现有持久化模型继续使用。可增加兼容旧记录的接入类型/说明，以准确区分 API 组装与原生改写；不重写旧记录的解释或历史摘要。
- 原生分支的 cc_prepared 表示改写后、原生传输前的中间值，页面不得将其默认标成重新生成 CLI 提示词，也不能称为最终出站。
- wire_final 的生产能力仍按实际支持情况显示。离线结果只能由独立 TLS 接收器的实体字节及有序 rawHeaders 补充，保留真实来源和缺失状态。
- 重测样本新增到独立证据目录，导入前后校验现有 89 条详情投影哈希；新详情中的凭据统一先注册再脱敏。

## 6. 影响范围与回滚

- 主要文件：src/shared/{contracts,input,protocol}.ts、src/control/header-policy.ts、src/runtime/293/{job,cli,native,source-profile}.ts；按职责增加少量原生入站和参数校验模块，不扩张为通用框架。
- 必要同步：共享日志解码/页面路径标识、单元/集成/原生/浏览器测试、docs、构建和精简接纳身份。
- 原版源、vm2api/cc2api 仓库和旧精简文件保持原状。新产物输出新路径，不覆盖旧可用产物；身份准入依照现有流程以全部验证为前提。
- 回滚以本任务精确文件范围和新候选产物为单位，保留失败证据，不撤销用户已有缓存或其他任务改动。

## 7. 验证与具体风险

- 先验证新原生路径能保留当前 SDK 的发送上下文，尤其 native CCH 与 session/querySource；这是新增路径的首个技术关口。
- 缓存、消息签名和工具历史不能因规范化而改变；原生与 API 路径分别验证，防止将旧 API 提醒插入原生历史。
- raw thread 续轮不能以当前文本重算会话后缀；缺失或冲突归因必须显式失败。
- 新构建可能改变分发体积及启动成本；重新验证身份、可复现性、独立部署和预算，速度如实记录，不用旧相对门槛替代安全验收。
- 全部执行只用无外网回环与合成凭据；官方原始抓包和完整原生提示词不进入 Git。
