# Brief — 原生 CC 入站保真适配与全场景回归

## Goal

- 支持原生 CC 293 请求保真接入，保留普通 API 的原生组装能力，并完成全部场景回归。

## Scope

- 增加原生入站识别、字段保留、必要身份改写及上下文一致性检查。
- 增加发送前参数校验，定位并修复强制工具选择、工具续轮、带历史子代理的三项超时。
- 重测原 23 场景，新增原生正文、缓存、线程、六类归因和反例矩阵，更新页面样本。
- 重新构建和核验精简运行时，记录体积、初始化、首轮及暖请求时延。

## Non-Goals

- 不改 cc2api/vm2api，不升级 303，不增加真实账号操作、付费推理、模型重试或本地工具执行。

## Technical Overview

- 入口区分原生 CC 与普通 API：原生请求保留已有 system、messages、tools、缓存及协议字段；普通 API 继续由 CLI 原生组装。
- 两条路径复用当前工作进程和同一 SDK 发送上下文，经必要身份改写后唯一发送；最终 CCH 仍由原生传输生成，独立 TLS 接收器观察与复算。

## Context & Decisions

- 固定官方 2.1.293，部署总量上限 27933052 B；沿用安全和兼容优先，不恢复旧相对速度门槛。
- 保留原生会话、prompt、轮次和父子归因；冲突明确拒绝。调用方凭据不外传，合法扩展头默认保留。
- 普通 API 保持现有字段支持范围；原五类字段在原生分支接纳，普通 API 负例仍按合同明确拒绝。
- 原有 89 条日志保持原状；新样本只走专用环境和无外网回环，最终采集缺失继续明示。

## Risks

- 首先要验证原生正文在同一 SDK 上下文中发送时，业务保真、归因和原生 CCH 能同时成立。
- 缓存、thinking 签名、线程后缀及错误收口可能受适配影响；模型规则只能依据固定 293 验证。

## Acceptance

- 原 23 场景及新增原生矩阵逐行有预期与实测；支持场景成功，不支持组合明确 4xx，三项超时均有根因和确定结果。
- 原版与新精简版通过关键原生矩阵及必需检查，全部已发送样本 CCH 独立校验通过；单次发送、无重放、无凭据泄露。
- 页面可查看新样本及实际路径，旧 89 条不变，桌面/手机通过；新产物身份、可复现性、独立部署、体积和时延证据齐备。

## Next Step

- 完成质量复核与规范更新，展示精确提交计划。
