## Bug Analysis: 将 CLI 入口标识误当作 CLI 请求装配

> 后续决定（2026-11-05）：用户已取消 vm2api 相对速度目标并接受当前延迟。下文关于继续追赶旧速度门槛的待办保留为历史，不再执行；原生 CLI、安全及隔离约束继续有效，当前处置见 [验收记录](./acceptance.md)。

### 1. Root Cause Category

- **Category**：E，隐含假设；同时涉及 B，跨层合同。
- **Specific Cause**：原适配器仍采用 SDK 的消息来源、非交互选项和空原生工具，只把进程 entrypoint 改成 cli。原生身份选择和终端提醒装配位于更上游的 CLI 查询上下文，User-Agent/billing 入口通过不能证明默认 system 和工具一致。

### 2. Why Fixes Failed (if applicable)

1. 只调整入口标签：实际 SDK 选项未变，头部检查通过但身份正文仍来自 Agent SDK。
2. 只调用底层 K_t：缺少 pie/OM、工具池、原生状态及 CLI 初始化，无法生成交互终端的完整提醒。
3. 只比较 -p：固定 293 的打印路径本身选择 SDK 分支，不能作为用户明确要求的交互终端目标。
4. 只减少第二个 SDK 客户端：保持了响应独占并消除了重复工作，但完整 CLI 默认装配的每轮成本仍存在，五轮配对速度没有因此通过。

### 3. Prevention Mechanisms

| Priority | Mechanism | Specific Action | Status |
| --- | --- | --- | --- |
| P0 | 参考验证 | 每个源版本直接采集未修改 PTY 主请求，标题 auxiliary 单列，打印模式单独分类 | DONE |
| P0 | 行为对照 | 对原版和精简版分别比较完整工具、提示词、提醒、参数及实际头，逐份核验最终 CCH | DONE |
| P0 | 单轮防护 | 一次构造/发送守卫，SDK 不接收 Response，本地工具拒绝，取消与错误退役且不重放 | DONE |
| P0 | 性能准入 | 对最终哈希重新跑固定配对脚本；失败不沿用旧 SDK 产物的通过结论 | DONE，当前性能未通过 |
| P1 | Spec | 将 CLI 与 -p、原生提醒装配、资源无损转换和双重身份知识交给后续 Update-Spec 评估 | TODO，遵守阶段顺序 |

### 4. Systematic Expansion

- **Similar Issues**：cc_prepared 与 wire_final、原版来源 SHA 与实际 memfd SHA、HTTP/SDK 参考与交互 CLI 的默认工作量，均不能仅凭标签视为等价。
- **Design Improvement**：原版和静态入口共用绑定表及装配代码，输入省略/显式空值分开，秘密处理统一在持久化边界。
- **Process Improvement**：不因一个入口或字段通过而扩大结论；比较工具、默认参数及实际发送量，记录失败候选和明确归一化规则。

## 性能排查的假设与证据

初始假设为 H1 完整 CLI 默认装配占主要成本 60%、H2 大正文序列化和 IPC 25%、H3 重复 SDK/JIT 初始化 15%。这些是排查优先级，不是已经测得的成本比例。

- 去掉第二个客户端后，五轮暖中位数仍为 33.782 ms，对照 11.316 ms；H3 下降。
- 对原版单作业 CPU 采样发现 native JSON 哈希、私有帧序列化及 URL 脱敏正则；保留功能，消除重复编码/扫描并并行采集与发送。新候选固定 HTTP 配对为 29.278 ms，对照 11.727 ms，仍未通过，不能将不同批次差值解释为确定收益。
- 字节码原始执行体研究约 167 MiB；单轮研究对照暖 45.801 ms/15.219 ms，未证明暖收益。该研究不是正式压缩分发文件，不用于正式启动验收。
- 新增实际工作量记录：固定 HTTP 夹具下，候选正文 126888 B、27 个工具；标杆 6464 B、无工具声明。保留官方地址的独立 TLS 接收下，同一性能业务输入为 92012 B、13 个工具。故补做 TLS 条件对照，以区分夹具与装配差异；不修改原输入、标杆或验收门槛。

当前最支持 H1，H2 也有实测依据；尚不能声称找到能达到 1.10 的方案，或证明该目标在所有可行优化下绝对不可能。性能仍是未完成项。

## 本轮检查修复研究

- FBK-001 的根因是跨进程合同缺少握手前的错误帧，入口丢弃 BridgeError，控制层又将空输出退出统一解释为 runtime_exit/502。已增加有界、脱敏的 worker_error/503，同步动态与静态入口；22 个协议/生命周期聚焦用例、3 个错误输出用例通过，原版与修复候选均通过已拒绝合成密钥的连续两次 HTTP 请求验证。
- CHK-002 的公开注释已经修正，准确描述首次受控发送与响应收口；没有用注释替代实现检查。
- 固定 Bun 实测支持 BUN_JSC_ 前缀和 unsafe.setJITPolicy，早期使用 JSC_ 的探针没有生效。三个激进阈值组合、原生 CLI 就绪策略重置、最小预热、同步元数据读取和仅同轮命令筛选研究均未证明能达到暖复用门槛；未纳入生产。研究对照都保持原输入和标杆，原始结果在 artifacts/cli-alignment-20261105T064401Z/repairs。
- 将同一旧载荷提取并按原配方重建 O2 加载器，分发哈希与旧候选完全一致。五轮交错的纯加载阶段 O2/O3/O3-LTO 中位数为 1584.698/1567.807/1588.494 ms，O3 仅改善约 17 ms；该研究不代表完整请求达标。
- 终端 local/local-jsx 命令的 load/call 原先将终端 UI 与执行依赖携入闭包。现已采用仅阻断这类执行入口、保留元数据和 prompt 技能的裁剪，原版与修复候选的最终正文对照通过；产物与证据见下节。

## Bug Analysis: 握手前的配置错误被包装成普通退出

### 1. Root Cause Category

- **Category**：B，跨层合同；同时涉及 C，传播遗漏，以及 D，初始化失败覆盖不足。
- **Specific Cause**：动态和静态入口丢弃本地 BridgeError，私有协议只能表达成功握手，控制层将未握手的空输出退出统一解释为 runtime_exit/502。服务创建阶段的只读验证不能代替首个作业的惰性初始化验证。

### 2. Why Fixes Failed (if applicable)

1. 只验证文件和路径：无法触发子进程内的密钥拒绝及本地确认失败。
2. 只打印固定 stderr：避免了泄密，但控制层没有结构化错误来源，无法保留稳定类型、状态和受控原因。

### 3. Prevention Mechanisms

| Priority | Mechanism | Specific Action | Status |
| --- | --- | --- | --- |
| P0 | 明确跨进程合同 | 握手前专用 worker_error，固定 native_configuration/503、无请求归属、严格字段和长度 | DONE |
| P0 | 单一错误出口 | 两份入口共用脱敏输出函数，等待写入回调后退出，未知错误用通用文本 | DONE |
| P0 | 失败隔离 | 错归属、握手后错误帧仍按协议故障处理，失败进程退役且不重放 | DONE |
| P1 | 原生回归 | 原版和精简版均验证连续两次已拒绝合成密钥、拒绝记录不变和零发送 | DONE |

### 4. Systematic Expansion

- **Similar Issues**：惰性初始化与创建服务的验证边界不能混同；未知异常与可以公开的本地合同错误也不能共用原始堆栈输出。
- **Design Improvement**：公开 schema 1 保持不变，启动失败只扩展版本绑定的私有管道，动态/静态入口共用实现。
- **Process Improvement**：修复错误传播时同时覆盖输出、解码、时序、退役和 HTTP/持久日志结果，不能只断言测试进程退出。

## 折中方案的静态复用复盘

### 1. Root Cause Category

- **Category**：E，隐含成本假设；同时涉及 C，生成依赖识别。
- **Specific Cause**：完整 CLI 装配开销不能等同于纯正文格式化。直接缓存整个 VA 会跳过 memory 读取、原生状态更新及钩子；通用 Map/JSON 键缓存的编码和闭包成本也可能抵消纯文本生成的节省。

### 2. Why Fixes Failed (if applicable)

1. 首个六工厂 Map/JSON 键原型的功能对照通过，但两轮同窗口研究未证明加速，未作为当前实现。
2. 改为每个工厂只保留最近一次可缓存的条件和结果，命中直接比较原始值；动态读取与外层原生处理仍逐轮执行。五轮旧/新研究暖中位为 32.088/31.172 ms，主线程 CPU 为 29.240/27.403 ms，只能证明本批小幅改善。
3. 正式原脚本的启动/首轮/暖比值为 1.094/0.542/2.490。前两项通过，暖复用仍失败，不能从文本缓存推导为整体达标，也不把不同批次的绝对耗时相减当作收益。

### 3. Prevention Mechanisms

| Priority | Mechanism | Specific Action | Status |
| --- | --- | --- | --- |
| P0 | 依赖闭合 | 固定六工厂及两纯辅助函数摘要；条件读取逐次执行，未知函数/位置拒绝构建 | DONE |
| P0 | 动态隔离 | 不缓存 VA、LT/Uz、sections Map、memory、权限、工具选择或请求正文 | DONE |
| P0 | 有界存储 | 每工厂单项，单项 UTF-8 键和值 ≤64 KiB；异常和超限不入缓存 | DONE |
| P0 | 同窗口比较 | 旧/新/标杆研究与原两方五轮准入分开，保留全部样本及失败结论 | DONE |
| P1 | Spec | 全部性能问题闭合后再推广可执行合同，不将小幅收益写作达标保证 | TODO |

### 4. Systematic Expansion

- **Similar Issues**：静态字符串、环境配置、项目读取、会话状态和最终正文是不同生命周期，不能因输出短期相同而共享可变结果。
- **Design Improvement**：保留原版对照，静态改写只作用于纯工厂，原生组合、动态段落、钩子及 CCH 继续处理当前请求。
- **Process Improvement**：先测缓存自身成本；按最终哈希重跑原生、独立部署、重复构建和速度，保留主线程 CPU 与总耗时的边界。
