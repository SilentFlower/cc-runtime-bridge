# 按账号支持无限内存并恢复11-5原生转发

## Goal

为账号提供明确的无限内存模式，并用于“11-5”，使其保持并发 2 使用原生转发。

## Background

- 用户明确选择“内存上限也取消”：账号进程使用整机可用内存，并与其他账号和服务竞争。此次决定取代此前的 2 GiB 总额方案。
- “11-5”的 bench ID 为 14、网关 ID 为 12、环境 ID 为 `15551aa6f302494cb9b5440750899c2c`。现有后端为 `native293`、并发为 2、RAM 为 `1536m`、额外 swap 为 `2048m`。
- 生产最近十条请求均为本地 503，模型尝试为 0；sender 预算缺失。证据在 bench 私有 `.deploy/backend-switch-inspect-20261110-fd124b28/`。
- 池已按需创建进程。Python、Rust 另有静态 RAM 门槛，入口为 `orchestrator/native_sender.py:17`、`cc2api/src/service/native_runtime.rs:72`。
- 用户已授权服务器调整。本轮覆盖实现、验证、联合镜像交付和生产生效，Git 与发布沿用各自门禁。

## Requirements

- R1：支持按账号显式无限内存。“11-5”的网络、CLI、sender 及派生评审使用整机可用 RAM/swap，实际 cgroup 显示无限制。
- R2：该模式独立于 sender RAM 配置及静态并发内存估算；并发保持 2，物理进程上限保持 4，沿用加权准入、按需创建和空闲回收。
- R3：固定二进制及映像校验、身份与凭据归属、工作隔离、取消收口和单次提交保持。CPU/PID、并发/RPM 沿用原策略。
- R4：有限账号沿用原校验，全局默认保持有限配置。生产只迁移“11-5”的内存模式，其他账号资源策略保持。
- R5：配置、Docker/cgroup、CLI 指标、物理特征和评审交接一致表达无限制；未知配置及观察失败明确报错。
- R6：使用合成凭据和离线 TLS 验证后交付同批镜像，空闲迁移生产。保存身份、HOME、会话、凭据及成果。US 沿用免备份、免宿主 RAM 重新估算的选择。

- R7：按账号开启二进制已有的 CC 组装后内容采集，请求详情展示头名称、值与正文；凭据脱敏，保留上限明确，截断和采集失败可见。

## Acceptance Criteria

- [x] AC1：账号三个角色及评审 Docker RAM 为 0、合计 RAM/swap 为 -1，实际 cgroup 两种上限均为 `max`（R1、R5）。
- [x] AC2：无限模式缺省 sender 预算时完成原生准备；离线 2 普通/4 Haiku、排队、取消和回收通过（R2）。
- [x] AC3：错误版本/摘要、身份/代次冲突继续拒绝；有限预算不足和未知模式继续拒绝，普通转发回归通过（R3、R4）。
- [x] AC4：CLI 指标、物理特征及评审交接识别无限额，界面显示“未限制”，缺失/异常按原状态展示（R5）。
- [x] AC5：生产“11-5”后端与并发保持，原生能力准备正常，cgroup 无限额，身份/会话/成果摘要一致；其他账号策略一致、健康及两库检查通过（R4、R6）。

- [x] AC6：合成请求的重复头、正文及组装阶段展示正确；凭据脱敏，超限截断、轮转及失败状态通过验证；仅为目标账号开启（R7）。

## Non-Goals

- 全机或其他账号批量取消限额。
- 新增资源编辑页、改变内存以外的限额或升级官方 CLI/二进制。
- 最终 TLS 写出采集和自动发起真实账号付费推理。
