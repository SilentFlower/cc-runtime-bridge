# 入站请求头协议白名单

## Goal

在桥接边界采用出站协议白名单，统一清理代理、CDN、new-api 与其他客户端的额外请求头，使进入上游构造的调用方字段具有明确归属。

## Background

- 用户将前置处理范围限定为请求头过滤，并明确选择协议白名单，要求参考 vm2api 及本项目此前抓包确定受支持字段。
- 当前 `src/control/header-policy.ts:37` 处理连接级、凭据、运行时及上下文字段；其余格式合法的请求头在 `src/control/header-policy.ts:55` 默认进入透传集合。
- `src/runtime/293/job.ts:282` 将透传集合合并到原生构造的发送参数，调用方同名完整值覆盖 SDK 默认值。
- vm2api 的 `src/lib/identity/crs-headers.mjs:23` 定义协议头白名单；`extractClaudeCodeHeaders` 只提取登记字段。合成输入验证确认代理、CDN、网关自定义及未知扩展头在其 Node 组装层被过滤。
- 历史抓包及固定 293 字段定义的研究记录见 `research/header-inventory.json`、`research/native-header-definitions.json` 和 `research/findings.md`，头名按入站、发送前、最终 TLS 和响应阶段分别归类。
- 本项目 `docs/header-policy.md:7` 原先约定合法端到端扩展头默认保留。本轮按用户选择将其改为显式白名单合同。

## Requirements

- R1：采用明确的入站协议白名单，登记字段参考 vm2api、固定 293 现有字段定义及本项目此前抓包。名单之外的格式合法附加头统一过滤，覆盖代理、CDN、new-api 与其他客户端私有字段，匹配忽略大小写。合法的未登记 `x-claude-code-*` 同样遵守该规则。
- R2：普通 API 与原生 Claude Code 入站遵守同一已确定的过滤合同，HTTP 入站头及内部信封头均受该合同约束。
- R3：过滤决定逐项记录字段名、动作和原因，原始入站采集继续遵守已有脱敏与保留规则。
- R4：继续遵守既有鉴权来源、运行时字段归属、版本能力、会话及父子代理关联合同，保持业务正文语义和单次发送合同。
- R5：继续明确处理已知字段的非法格式、重复项及上下文冲突，过滤名单外的重复附加头时逐项记录动作；后续额外扩展头通过显式登记纳入兼容范围。
- R6：白名单约束调用方可带入原生构造的请求头，运行时自行产生的鉴权、身份和传输字段继续遵守各自归属。上游响应头继续遵守既有响应合同。

## Acceptance Criteria

- [x] AC1：已确定的代理/CDN 字段在大小写变体、重复项以及两类入站中均具有明确的过滤结果。
- [x] AC2：合成凭据与离线回环验证显示被过滤的字段未进入最终发送观测，业务正文及会话、主子代理关联符合既有合同。
- [x] AC3：日志中的入站采集与头部处理决定具有对应关系，过滤原因可见，采集阶段与完整性标记符合已有合同。
- [x] AC4：未知客户端头和未登记扩展头按白名单合同过滤，受支持字段及既有多值行为具有可复现验证。
- [x] AC5：历史可观测协议字段与固定 293 的可选工具耗时、压缩状态字段均有明确归属。测试控制字段通过夹具私有通道设置，实际响应场景仍可逐项验证。

## Out of Scope

- 工具参数组合校验、消息自动修补、模型或运行时升级、真实账号与付费推理验证。
- 独立的透明 HTTP 代理或分布式追踪功能。
