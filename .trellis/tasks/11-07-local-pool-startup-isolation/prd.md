# 本地池启动诊断与故障隔离验证

## 目标

让本地池初始化失败能够安全定位到具体阶段，并验证启动失败、取消或客户端异常退出后资源可清理、其他会话可继续。

## 背景与已确认事实

- 用户已要求继续启动稳定性和双客户端故障隔离排查，验证使用合成凭据和离线假池，真实模型调用为 0。
- P2（实施前基线 b6312a1）：前一轮一次 local_pool_startup/503 发生在初始化阶段，触发点为 `tests/local-pool/gateway.test.ts:254`；单场景及完整串行复跑通过，原始原因尚未定位。证据：`artifacts/native-purpose-fix-20261107T040107717189Z/integration.log:32`。
- P2（实施前基线 b6312a1）：`scripts/testing/local-pool-engine.ts:75` 将证书、Node TLS 接收端和隔离驱动启动错误合并成同一说明；`scripts/testing/pool-forwarder.ts:134`、`scripts/testing/local-pool-driver.ts:83` 的私有 fatal 帧也不保留具体安全原因。
- 本轮累计 48 次实际初始化及关闭成功、模型调用为 0，未观察到本轮遗留的直接子进程或新增临时目录。其中后 16 次逐次采到 TLS 握手成功；前 32 次附加观察器未加载，单独保留采集缺口。详见 `research/findings.md` 和 `research/startup-evidence.json`。
- 原有 UND_ERR_SOCKET 属于另一个未定位现象，不能以本任务的启动探测或正常回归通过替代其根因证据。

## 需求

- R1：保留初始化失败阶段和受控原因，未知明确为 unknown，不输出原始异常、stderr、URL、证书正文或凭据。
- R2：以实际冷启动、连续和并发启停检查资源释放与下一次启动，模型预算保持零；不通过自动重试掩盖失败。
- R3：两个真实 Claude Code 客户端共享合成 HOME/config/cwd，使用独立会话且各创建 3 个实际 Explore 子代理，验证活动取消、排队取消、异常退出及另一会话继续，核对响应、会话、子代理和账本归属；至少一个故障场景发生在子代理调用中。此项作为诊断及恢复行为的隔离回归。
- R4：模型转发预算、身份、单次发送、最终采集及日志保真合同保持；启动问题不通过放宽 TLS 或隔离校验处理。

## 验收条件

- AC1（R1）：受控证书、TLS、自检、隔离驱动及私有通道初始化失败能区分阶段与安全原因；未识别错误明确未知，旧私有帧兼容，合成秘密不进入新诊断。
- AC2（R2、R4）：失败初始化产生零模型调用，尝试清理自身全部进程和临时资源，下一独立初始化可成功；清理异常不得覆盖初始失败证据。
- AC3（R2）：连续和并发启停报告逐次记录成功、失败和缺失证据，不能把复跑成功当作原始故障已修复。
- AC4（R3、R4）：两个实际 CLI 的取消和异常退出场景中，未被取消的会话成功继续；排队取消不发模型请求，已发取消最多发送一次且不自动重放，响应和父子归属无跨会话污染。
- AC5（R1–R4）：类型、定向单元、离线本地池及相关原生检查通过；零真实账号或付费调用，原有无关变更保留。

## 范围外

- 不触发真实账号或付费推理，不修改用户代理或池配置，不宣称已定位原始 UND_ERR_SOCKET。
- 暂不修改取消机制或扩展外部 API；如验收发现新的行为缺陷，先补齐同场景证据与对应设计。
