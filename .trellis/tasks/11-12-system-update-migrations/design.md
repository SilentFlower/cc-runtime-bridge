# 自动迁移与恢复设计

## 1. 目标和边界

- 统一现有 v3 的 `bench/db.sqlite` 与 `gateway/gateway.sqlite` 数据版本、迁移执行、恢复和验收。新代码进入现有平台/账号联合镜像；管理员日常仍使用系统更新页面。
- 用户已选择升级前保存两库快照。默认保留最近两组已完成快照与所有活动恢复依赖，保护磁盘占用和恢复完整性。
- 一个任务交付完整链路。合同、迁移、快照、发行和页面互相依赖，以集成验收为完成边界。

## 2. 已有边界及调用位置

- `system_updater.py::_execute` 所有排空、阶段持久化与恢复；`HostDeployment` 所有容器、数据根、门禁与配置 CAS。
- 两库位置来自固定部署数据根和实际控制服务挂载，拒绝外来路径、链接或未知数据库驱动。
- bench 的 SQL 初始化分布于 main、账号运行时、凭据归属、工程/计划等模块；gateway 的初始化为 `store::db::init_db/migrate` 及用量、诊断、调度子模块。实施时从实际定义提取迁移，不通过创建完整运行服务触发模型或账号活动。
- `storage_backup.py` 已有 SQLite backup API、逻辑摘要和权限恢复依据；本功能单独操作两个数据库文件，避免调用全目录备份复制 HOME 或工作区。

## 3. 版本化迁移与兼容合同

### 新增迁移目录合同

- 新增每库迁移登记，字段为 `id:String`、`version:u64`、`predecessor:u64`、`checksum:SHA256`、`engine:sqlite`、`kind:schema|data`、`rollback_mode:compatible`。定义来自仓库内受控迁移模块，版本严格递增，登记后校验和不可覆盖。
- 每库新增 `system_schema_migrations` 台账：`migration_id TEXT PRIMARY KEY, version INTEGER NOT NULL UNIQUE, checksum TEXT NOT NULL, applied_at TEXT NOT NULL, operation_id TEXT NOT NULL`。单步变更及台账在可事务处理的 SQLite 事务内提交。相同 ID/摘要重复执行为完成；同 ID 不同摘要、缺前驱或未知结构拒绝。
- 首版建立现有初始化基线。提取数据库专属定义及其依赖到明确迁移所有者，保持现有初始化顺序、默认值、条件回填和账号归属。已有库在结构核验后登记基线；空库复用相同入口。结构核验使用冻结基线的必需表、列、SQLite 类型亲和及主键；支持兼容新增字段。未登记旧库先检查稳定核心字段，迁移结束和已登记库复核完整最低结构。
- 初始迁移同时冻结其 SQL 命名空间转换、默认设置和历史身份画像。纯模块内直接保存这些已读取的定义，避免后来业务默认值间接改变已登记迁移。原命名空间入口保留导出兼容。
- 稳定数据合同由迁移定义、版本和语义校验和生成。普通服务查询、日志和页面改动不纳入摘要。新增迁移必须登记，CI 对未登记数据库变更给出具体缺口。
- legacy 合同到新基线使用明确映射和真实旧库升级证据；记录已读取的旧发行摘要，证据失效即停止发布兼容声明。常规新增迁移的旧程序兼容许可由受控验证结果生成。

### 新增固定维护入口

- bench 提供独立数据库维护入口 `python3 -m database_migrations plan|apply|verify`；gateway 提供 `claude-code-gateway database-migrations plan|apply|verify`。本节命令为拟新增接口，实施时统一定义参数和测试。
- 固定参数为 `--operation-id UUID`、`--target-version u64`；bench 数据路径固定为部署内 `/data/db.sqlite`，gateway 连接解析复用现有配置。宿主构造参数和镜像摘要，发行材料只引用登记 ID，禁止携带任意命令或文件路径。
- 输出有界 JSON：`database, current_version, target_version, steps:[{id,version,checksum,state}], state, reason`。错误退出非零；日志不包含记录内容、凭据或数据库连接秘密。
- 离线维护容器只挂载所属数据库目录及本次结果目录，关闭网络、去除能力并采用只读程序层。迁移入口不创建业务路由、账号运行时、线程调度器或模型客户端。

## 4. 发行格式与旧底座接入

- 现有 v1 校验严格固定字段和 `compatibility.updater=1`。新迁移发行采用 v2，声明 updater=2，并新增受签名绑定的 `migrations` 计划与兼容验收材料引用；继续核验组件与联合清单原字节摘要。
- 计划资产仅允许固定文件名 `database-migrations.json` 和 `database-compatibility.json`，包含大小与 SHA256；内容绑定父源码、双端镜像摘要、源合同、目标合同和迁移登记，限制大小及字段。
- v1 目录 `updates/v3` 保留原格式并刷新签名有效期，仅列出旧执行器支持的发行。v2 使用独立受信目录 `updates/v3-migrations`，避免旧执行器检查目录时因新格式整批失败；新执行器验证 v1 安装历史和 v2 目标，维护独立目录序号。
- 增加受控的本地底座能力升级入口：默认预览，核对固定源码清单、旧/新 SHA、当前安装、无活动操作、门禁和服务锁；明确 apply 后更换精确执行器文件并切换受信通道。失败恢复旧源码、策略及服务，保留 current/history/epoch 和凭据归属。首次接入保存可独立回读的恢复日志；未完成日志阻止新接入，并提供按 UUID 的恢复预览及 apply，允许服务 inactive 时核对精确原/新值后恢复原源码、策略、状态及服务。
- 底座接入属于一次操作，按项目既有专项运维边界执行；本任务提供脚本与隔离验收。生产执行另行授权。之后有迁移的常规发行由页面安装完成。
- 本次旧预热发行的源码随新发行进入；验证从已记录旧合同到新基线的迁移路径，使既有页面通过新的宿主接口获得可安装结果。

## 5. 两库快照与磁盘边界

1. 下载/验签、空间预检、暂停新准入并排空现有活动。
2. 冻结原身份和环境，停止两个控制服务，检查本部署数据库写入者及后台任务已退出。
3. 在本次操作私有目录用 SQLite backup API 保存两库，包含 WAL 中已提交内容；执行 integrity/逻辑摘要校验，保留原权限、uid/gid，fsync 文件及目录。
4. 原子提交两库共同完成回执后才进入迁移。任何一库失败，整组快照不能用于恢复。

- 回执字段：`schema_version, deployment, operation_id, epoch, source_release, databases:{bench|gateway:{relative_path,size,sha256,logical_sha256,uid,gid,mode,schema_version}}, completed_at`；公开 API 只返回状态、大小和时间。
- 私有目录0700、文件0600，拒绝链接、特殊文件、越界路径与外来部署。快照中含敏感数据，日志和浏览器只显示摘要状态。
- 空间预算覆盖当前两库逻辑页大小、WAL、快照与恢复暂存，以及安全余量；沿现有镜像准备空间预检独立复核。空间不足保持原版并给出预计需求，不以删除受保护快照继续。
- 默认保留最近两组已完成快照，另外保护活动/待恢复引用。仅在成功提交及完成标记校验后轮换精确操作目录；未知来源、损坏、外来目录保留并报告。

## 6. 状态与恢复

正常状态：`preparing → draining → snapshotting → migrating → switching → verifying → committing → cleaning → succeeded`。

- `snapshotting` 包含停止控制服务及共同快照；该阶段失败应重新启动原控制组合并验收、释放原门禁。
- `migrating` 在候选镜像的固定维护入口逐库执行并保存逐步结果；通过后启动候选控制服务。常规启动复用迁移所有者核验台账，避免在业务启动阶段重复执行未知迁移。
- 候选镜像、schema、台账、核心数据、身份、环境与业务读写验收通过后，提交安装记录；以持久单向 `release_started` 标记界定重新开放准入。
- 快照之后且 `release_started=false` 的失败进入 `restoring_data → restoring`。停止两端，复核原操作与 epoch，将已校验的两库快照写入各自暂存文件并 fsync，逐项原子替换及记录进度，处理本次 WAL/SHM，恢复原程序与环境并验收。
- 账号重建后的运行角色登记独立于业务数据恢复：恢复双库前冻结本操作已登记环境的六项生命周期字段及原身份，恢复后在事务内续接这些登记，再交由原运行时收口候选角色。保存原快照值与续接值作 CAS，保持环境代次前进并保护外来变化。该恢复绑定及应用完成标记先于原程序启动持久化。
- 两库替换不是跨库原子事务。持久恢复日志和持续关闭的门禁保证中断后继续完成同一组；恢复完整前不开放服务。替换意图在副作用前落盘，恢复重试核对精确当前/暂存/目标摘要。
- `release_started` 在开放门禁前持久化，之后禁止用升级前快照覆盖数据库。安装完成后显式回退使用旧程序对当前数据的已验证兼容路径，保留后来业务写入；未知状态进入 reconcile。
- 不使用自动 down SQL 逆推数据。旧版兼容的增量结构允许保留；数据恢复仅用于本次未接单安装失败。
- 取消仍只覆盖准备和排空，迁移开始后沿原操作恢复，不创建重复操作。

## 7. 页面与接口

- 延用现有状态/发行/操作 API 和冻结 UUID/revision/摘要。新增迁移摘要、快照状态、源/目标版本、有限原因码，`data_compatible` 保留为旧页面可识别的可在线安装结论；新版同时显示判定依据。
- 正常展示“可自动迁移”“保存数据库快照”“执行数据库迁移”“恢复数据库”等阶段；底座能力、迁移路径、空间或校验失败分别解释。
- 两个控制服务停止时页面沿现有重连机制展示连接状态；重连后读取持久进度，禁止将断线缓存当作实时证据。新页面沿既有暖色样式、串行轮询和确认窗口归属。

## 8. CI、验收与交付

- 构建候选及受支持历史镜像后，以无网络、合成凭据和独立两库生成真实旧状态，验证旧数据→新迁移→候选读写→旧程序读写，以及重新执行、空库和未知结构。
- 每个兼容声明绑定原版/候选实际镜像、数据合同和证据摘要。CI 校验全部成功后发布签名清单和对应通道目录；单元测试替代不了实际镜像迁移演练。
- 故障覆盖 WAL、两库部分完成、磁盘不足、快照损坏、停止/恢复中断、迟到操作、已重新接单、台账摘要冲突、维护门禁和快照轮换。
- 交付顺序：cc2api 子仓、bench 父仓及子模块引用、主仓任务/验收材料。生产底座升级、安装和真实数据库操作沿独立上线流程。
