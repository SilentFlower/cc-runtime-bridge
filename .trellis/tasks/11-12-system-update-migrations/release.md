# 上线准备与验收

## 交付范围

- cc2api：迁移基线、台账和固定维护命令，原 PostgreSQL 入口保持原迁移语义，系统更新页面及类型。
- bench：稳定合同、签名 v2 与独立通道、真实旧镜像兼容演练、双库快照/迁移/恢复、一次性底座接入工具与 SOP。
- 主仓：任务材料及隔离机器证据。其它任务按各自所有权交付。

## 上线前固定

- 按 cc2api → bench 子模块引用 → 主仓任务材料的顺序核对精确 Git 交付。CI 使用干净提交构建。
- 签名发行必须包含迁移计划和实际兼容演练证据。核对原生产发行的完整清单 SHA 已出现在来源证据中。
- 固定目标宿主、原安装、策略路径、systemd 服务名、公钥、源码清单 SHA、两个数据库挂载和资源参数。
- 实际生产接入与数据库操作按独立上线授权执行。

## 一次性底座接入

1. 按 `deploy/v3/SYSTEM-UPDATES.md` 预览 `upgrade_system_updater.py` 的精确计划。
2. 复核原操作已完成、门禁空闲、服务归属及恢复副本后，授权并执行同一计划的 `--apply`。
3. 核对原 current/history/revision/epoch、账号及内核归属，确认接口 `migration_capability=true`。
4. 页面检查新通道，确认该生产来源具有可执行的迁移路径。

## 首次迁移安装验收

- 页面冻结版本和原 revision，排空后停止双端、校验两库快照，再执行固定离线维护入口。
- 核对两库台账版本与目标计划、受保护身份与资源、账号原运行状态、控制服务精确镜像和原预热功能。
- 核对 `release_started` 先于恢复准入落盘，页面能重连并读取持久完成状态。
- 查看快照轮换结果：最近两组及活动恢复引用保留，异常快照目录保留供核验。

## 异常路径

- 本次安装尚未接单时，按原操作恢复同组双库及原程序。
- 已经重新开放准入时，使用保留当前数据的兼容回退。
- `reconcile` 按原 UUID/epoch 核对进程、配置和维护门禁，再恢复原操作。
- 底座接入异常使用 `updater-upgrades/<UUID>` 中的精确源码、策略、状态副本和完成记录核验。使用同入口 `--recover <原UUID>` 预览恢复，复核后追加 `--apply`。服务停机及恢复再次中断均沿原 UUID 续接。后来操作保持其恢复归属。
