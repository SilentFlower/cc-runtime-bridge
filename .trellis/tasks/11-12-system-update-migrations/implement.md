## 验证入口

- 先执行与改动匹配的 Python/Rust 定向测试，随后按实际影响运行完整检查；Python 使用 bench 现有 `.venv`。
- bench 执行现有 `test_system_*.py`、`test_system_update*.py`、新增迁移/快照/恢复测试和受影响初始化测试。
- cc2api 执行 `cargo fmt --check`、`cargo test --locked`、web 的 `npm run build`；保留 PostgreSQL 原迁移兼容验证。
- 扩展 `verify_system_update.py` 的真实 Docker 场景及 `verify_system_update_browser.py` 的真实页面合成 API 场景；所有数据库、签名和凭据均为隔离合成材料。
- 实际旧发行/候选镜像验证要求冻结来源、数据夹具、进程退出码、各库逻辑摘要、台账、发布证明、清理结果和模型请求计数；不将启动成功等同于升级可用。

## 失败收口和实施检查点

- 迁移定义、旧基线、受信格式和持久操作合同先在代码中明确，再跨层实现。
- v2 目录与一次性宿主接入必须一同验收；旧执行器能继续读取旧通道。
- 两库快照完整且可恢复是迁移前置条件；快照失败时恢复原控制服务并释放本操作门禁。
- 开放准入的持久边界先于实际开放，断电及回调迟到不能使数据库恢复越过该边界。
- 测试只清理本次标签、私有目录和容器。真实账号和付费推理计数为0。
- 实现阶段发现设计细节调整，先同步任务材料；新产品或生产授权边界按 owner 单独解决。
