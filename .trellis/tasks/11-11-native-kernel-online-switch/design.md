# 11-5 请求内核在线切换设计

## 边界与信任

cc-runtime-bridge 在发布端提供版本化制品、受信清单和离线准入证据。清单固定 schema、发布 ID、平台、字节数、官方版本和来源摘要、分发摘要、实际执行体摘要、worker 协议及资源合同。使用独立发布签名和底座内固定验证公钥；私钥仅在发布端。保留镜像内置 beta.3 固定身份作为兼容基线。候选须经真实行为回归，版本字符串不作为兼容证据。

bench 负责受控源下载、版本目录、升级状态和现有管理端界面。按精确发布 ID 和摘要寻址，限制来源、大小和超时；暂存验证后原子发布，已引用内容不可覆盖。首次底座为 sender 挂载只读版本目录；浏览器或业务请求不能指定下载 URL、文件路径、密钥或命令。账号可写 HOME 与制品目录隔离。

cc2api 管理账号入场、凭据和 sender 控制权限。sender 独立校验受信清单，保留精确 FD 启动及真实 memfd 摘要和封存核验。分发体、共享映像、池和预热结果绑定内核摘要及内核代次；账号环境代次、设备、资源和凭据归属仍独立验证。普通预热迟到结果不能写入新代。

## 状态和操作

1. 管理端从现有管理员边界提交准备、激活或回滚，提供精确候选和预期账号环境代次。以操作 ID 幂等，前置状态版本绑定环境代次；新操作消费该版本，迟到请求不能在之后的回滚上重新激活。状态区分准备、排空、预热、已生效、已恢复和待对账，公开实际版本/摘要及脱敏故障码。
2. 复用网关账号入场门和 sender 活动核对，阻止新 API 入场并等待本地流结束；占用未知时不切换。复用的排他租约要求当前 CLI 租约空闲；CLI 忙时延后切换，已运行的 CLI 不被终止。复核代理、账号、环境与凭据归属。
3. 在 sender 内先等待旧物理进程完成退出，再启动候选；超时按原失败恢复路径处理。普通后台预热会避开维护窗口；增加仅当前维护所有者可调用的切换预热，凭据仍由网关解析并经既有私有鉴权通道传递。成功要求真实 worker_ready、执行映像核验、暖进程和内核代次一致。释放入场门前提交持久版本指针与观察结果。
4. 失败在门内按原摘要重新预热原版；确认恢复后开放。用户回滚使用同一事务。排空超时且尚未切换时保留原版并释放本操作门禁。持久记录原版、候选、环境代次及操作所有权；重启后核对实际 sender 与持久状态。状态不明时维持可见恢复门禁。
5. 账号运行状态以实际 sender 就绪为准。制品回收保护所有账号的活动版、上一版和操作引用。
