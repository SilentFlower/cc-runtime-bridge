# 修复取消后的 TLS 采集准备竞态并发布平台补丁

## Goal

修复取消后补热进程与TLS采集器就绪衔接，验证后发布flower2api平台补丁供现有v3实例升级。

## Background

- 用户要求读取cc-runtime-bridge最新窗口的BUG并修复、发布新版，同时继续旧包清理与正式镜像改名。
- 已读取最近会话01a1c944-f680-7722-bcad-11ced376f8f6：10-30在取消前一请求后，两个新进程分别启动3.50/3.39秒，业务取用时采集仍为CAPTURE_PREPARING。配置与debug已开启。
- 实际实现位于关联仓vibecoding-bench的services/gateway/src/service/native_runtime.rs与native_tls_observer.rs。Worker::start在worker_ready核验后异步slot.warm并立即返回，NativeTlsCapture即时取用槽；采集准备与worker可取用之间存在窗口。
- flower2api当前平台元数据为v1.1.1。固定293内核及已准入制品继续原合同；此次按平台修复准备v1.1.2。

## Requirements

- T1：取消导致worker退役后，以现有身份、代次和物理容量约束及时补热；经过准备的后继worker在宣告采集ready之前完成同进程TLS探针预备。
- T2：后台补热按池键和代次合并；旧PID、旧采集代次及迟到启动结果保持隔离；维护、关闭、切换与取消优先。
- T3：采集启动及失败处理保持有界；业务仍最多一次模型发送，采集故障不触发请求重放、伪造成功或秘密泄漏。实际失败/超时/冷态仍公开真实受控原因。
- T4：采集关闭、未配置、旧镜像、账号容量及既有停止状态保持原行为。业务进程就绪、TLS就绪和单请求完整性分别表示。
- T5：建立修复前失败与修复后通过的同一取消/补热竞态证据；默认只使用合成凭据、离线回环及固定真实原生制品。
- T6：修复通过后更新平台补丁元数据，按原手动发行、签名、双库演练和序号合同发布并核对远端受信目录。生产安装由独立指令执行。
- T7：关联仓与本仓已有未提交任务、研究和日志按原归属保留；与镜像清理分文件协作。

## Acceptance Criteria

- [x] 首次后台准备、取消后补热、下一请求及连续请求的TLS状态/原文证据可关联，正常就绪路径消除本次竞态。
- [x] 取消、旧代次迟到、帮助进程超时、关闭采集及维护均通过；模型实际接收次数符合一次提交。
- [x] 物理许可不超限，旧进程与采集器收口，下一正常业务可继续。
- [x] Rust定向/相关回归、真实固定内核与隔离Docker验收通过；自动真实模型调用为0。
- [x] 平台补丁的CI、签名发行及原v3升级/回退合同通过，远端版本与源码来源一致。

## Non-Goals

修改固定内核身份、自动付费推理、生产安装、借修复扩大容器权限或重写采集协议。
