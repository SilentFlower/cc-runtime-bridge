# 任务交接摘要 — 原生上游配置与按需最终出站验证

## 目标

- 支持可选端点和模型，并在开启验证时采集最后一跳 HTTP 字节、对齐固定原版 CC 的传输特征。

## 范围

- 增加 Base URL、根模型覆盖和验证开关；未设置时保留原生选择，验证默认关闭。
- 内置 TLS 接收与原字节转发辅助程序，在最终写出通道采集。
- 更新实际模型、采集来源、健康状态、日志页和启动/构建说明。

## 不包含

- 复制完整 cc2api 网关、网页配置编辑器或账号管理。
- 自动付费推理、真实凭据文件操作、业务重组或 JS 最终 CCH 生成。

## 技术概览

- 关闭：前置 → 原版 CC → 上游。
- 开启：原版 CC → 验证器 TLS 接收 → HTTP 原字节透传 → 固定 293 画像的 TLS 写出通道 → 上游。
- 验证器不重新创建 HTTP 请求，CCH、账号身份和业务内容仍由原版 CC 生成；采集来自最后写出，不拿第一跳补写。

## 背景与决定

- 固定官方 CC 2.1.293，新增小型 Rust TLS 辅助程序，分别登记来源和构建身份。
- 原版诊断在复用连接时漏掉后续完整请求；同二进制 Node TLS 也不能直接替代原生画像。
- 可控 TLS 原型在 TLS1.3、TLS1.2、HRR、2 MiB 正文四组中，完整公开指纹与原版相同，最终 HTTP 字节与独立接收端完全相同，8 条 CCH 独立核验通过；真实模型调用为 0。
- 评审时完成可行性原型；批准后的实际实施进度及验收以 implement.md、research/acceptance.md 为准。

## 风险

- 开启验证后，对外 TLS 实现不同于官方 CC，需要维护画像、代理及证书兼容；不能称为全程官方传输。
- 连接生命周期、长流、取消和并发尚待完整验收；不承诺随机密钥或物理时延一致。

## 验收

- 普通/原生输入的四种覆盖组合正确；关闭验证无额外进程或二次发送。
- 最后一跳写出与独立上游逐字节对照，部分写出、失败、缺失和截断明确可见。
- 完整公开 TLS 字段、实际交换、TLS1.2/1.3、HRR、HTTP、有序头及连接复用/关闭/恢复策略对齐。
- 健康流超过 30 秒、慢消费、取消、错误，以及两个真实本地 CC 客户端各自多个子代理通过隔离验收，不额外重试或增加默认总时限。
