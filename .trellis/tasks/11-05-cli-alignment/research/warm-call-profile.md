## 采样边界与观察

- 所有进程使用独立 HOME/config/cwd、合成凭据和 unshare --net 回环。实际模型路径仅到本机 HTTP 夹具，真实上游请求为 0。
- 当前源码的分段探针通过原版固定 293 预加载运行六轮；单独记录权限/代理/技能、工具、提示词/附件、原生查询、K_t 构造、显式参数核验、传输及 SDK 收口。它包含观察代码，且不是当前精简哈希的正式性能结果。
- 本批分段显示，前置配置/技能通常约 2.6–3.6 ms，工具约 1.0–1.3 ms，附件和提示词的并行阶段约 6.6–8.7 ms，OM 首次模型调用前约 3.0–3.9 ms，K_t 到 fetchOverride 约 6.3–8.8 ms，暖传输约 2.6–3.8 ms。各并行子项的墙钟时间不能直接相加解释 CPU。
- 针对当前分发文件的 CPU 探针通过 BUN_OPTIONS 运行，保持相同被测文件；首个探针在 stdout 包装器中 JSON.parse 整帧，产生了明显的观察开销，因此不能把其中的 parse 样本当作产品热点。v2 改用固定前缀识别握手和空闲帧，原始结果分别保留为 compact-cpu.json 与 compact-cpu-v2.json。
- 环境读取计数显示，六轮中若干后端开关各读取约 5106 次。但调用次数不代表耗时占比，后续配对试验未证实它是主要瓶颈。
- 读取原生配置类确认 invalidateAll 会递增 epoch；原生 repoTierFreeze 也有正式的 engage/release 语义。原生功能判定还涉及环境值、配置来源与管理策略，不能仅凭 epoch 和一次结果相同就认定覆盖全部依赖。

## 配对研究

下表均为独立三方五轮研究：旧候选、新研究方案、固定 vm2api，奇偶轮反转，每进程六个作业。输入、响应、诊断消费及单次发送检查沿用正式脚本。只在同一行比较旧/新，不能跨批相减。

| 方案 | 旧 / 新暖中位 | 旧 / 新主线程 CPU 中位 | 本批结论 |
| --- | --- | --- | --- |
| 将研究进程环境复制为普通对象 | 29.671 / 28.124 ms | 26.054 / 24.279 ms | 暖耗时比 0.9479，CPU 比 0.9319 |
| 同一原生根内复用 firstParty 后端判定 | 25.469 / 26.086 ms | 22.390 / 23.560 ms | 暖耗时比 1.0242，CPU 比 1.0523 |

环境副本没有足够收益，且不应据此冻结凭据。后端判定复用没有改善。功能配置试验的墙钟耗时仅小幅下降，主线程 CPU 反而增加，且该研究键没有完成全部策略/上下文依赖证明，因此没有进入生产实现。

后端与功能配置两个试验直接运行未归档的研究执行体，只用于定位暖路径；它们的启动时间不含正式加载器解包，不能作为分发启动验收。各试验的实测 SHA、构建说明和样本在 provider-build.json、feature-build.json 与 benchmark-*/ 中。所有研究文件继续留在被忽略的 artifacts，不写入运行时接纳表。

另外对现有导出函数尝试定向 JIT，以及逐作业使用原生设置快照。前者没有证实足以达标；后者还需计入每轮约 0.4–0.5 ms 的快照建立和释放成本，不能只比较 runNativeJob 内的分段。两项仅为诊断，没有替换正式运行路径。
