# Brief — 独立二进制与 cc2api 转发方式接入

## Goal

- 交付独立二进制，在 cc2api 中按账号选择原生转发，并保留账号现有并发能力。

## Scope

- cc-runtime-bridge：原始请求输入协议、最新二进制构建、身份校验和离线验证。
- cc2api：账号字段、数据库迁移、管理界面、Gateway 分流及账号工作进程池。
- vibecoding-bench：V3 sender 的二进制接入、私有目录和资源预算配置。
- 新 beta 的 Linux x64 二进制附件、SHA256 清单及接入/回退说明。

## Non-Goals

- 旧 V4 整体升级、容器角色合并、独立管理后台。
- 官方运行时版本升级、任意端点透明转发或本地工具执行。
- 自动部署生产、切换真实账号和付费推理。

## Technical Overview

- cc2api 完成鉴权、账号选择和调度后，原生 Messages 在 Rust 协议改写之前分流。二进制统一执行输入校验、请求头白名单、原生组装、CCH 和唯一发送。
- 工作进程按账号及凭据代次隔离，按需启动并复用。每个进程执行一个作业，终态与 idle 收齐后释放；取消和故障收口对应进程。
- 网关继续负责凭据刷新、用量观察与流生命周期许可。工作进程仅取得当前 bearer 和受控身份。
- 首版在 bench V3 账号 sender 中执行；其他端点沿原有方式处理。

## Context & Decisions

- 已确定按账号选择，使用 `request_backend=legacy|native293`。历史与省略值默认 legacy，空闲时支持独立启用和回退。
- 已确定保留账号并发，通过按需进程池承载。沿用 Haiku 半槽规则：标准并发 3 可对应 3 个普通请求或 6 个 Haiku 请求。
- 内部运行时固定官方 2.1.293，原生入站沿该版本能力处理。原生方式使用运行时自身构造规则；既有 Rust 正文、头部、CCH 和 TLS 改写设置作用于 legacy。
- 原生模型请求保持单次提交，错误返回调用方。回退通过账号显式切换，凭据恢复供后续请求使用。
- 保留 network、CLI、sender 三角色。原生 sender 内存由部署侧显式配置，并在账号有限总预算中校验。
- 当前 beta.1 为源码发布，新版提供实际二进制。最终文件体积按新构建实测记录。
- 用户后续确认先优化内存再发布：共享经校验和封存的只读执行映像，额外空闲进程60秒后回收并保留1个暖进程；并发能力保持，预算按完整请求实测冻结。

## Risks

- 现有 sender 预算为 128 MiB。原生池预算需要根据普通及 Haiku 满并发实测配置。
- 凭据更新、并发调整、取消和迟到事件涉及代次与许可一致性，需要专项验证。

## Acceptance

- 独立部署实际二进制，双次构建、分发/执行体 SHA256 和体积可核对。
- 两账号分别使用新旧方式；账号迁移、管理配置、空闲切换及回退验证通过。
- 普通 API 和原生 293 的工具往返、thinking、协议头、会话/主子关联、JSON/SSE 与取消经离线 TLS 实收验证。
- 普通及 Haiku 加权并发、账号隔离、凭据代次、错误单次发送和许可释放验证通过。
- V3 隔离、有限预算、缺能力失败和旧后端回归通过。
- 新 beta 附件与最终源码提交一致，下载后的二进制校验及接入验证通过。

## Next Step

- 完成内存优化与实际V3验收，进入Check-All及Update-Spec，再展示精确三仓Git计划；随后发布并验收beta二进制附件。
